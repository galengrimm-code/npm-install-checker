### Key Files

- `npm-install-checker.js` (463 lines) — entire hook: stdin parser, npm command tokenizer, parallel registry/downloads/advisories fetch, typosquat (Levenshtein) check against a hardcoded popular-package list, scored result aggregation, JSON `permissionDecision: 'ask'` output
- `install.js` (87 lines) — copies the hook into `~/.claude/hooks/`, registers a `PreToolUse` matcher entry in `~/.claude/settings.json` with a 15s timeout
- `uninstall.js` (46 lines) — reverses the install: removes the hook file and filters the matching entry out of `settings.json`

### Data Flow

Claude Code fires `PreToolUse` before a Bash call → stdin JSON → `readStdin()` (2s timeout) → `parsePackageNames()` extracts package names from `npm install`/`npm i`/`npm add` commands, stripping flags and skipping local paths/tarball URLs → `checkPackage()` runs three npm API calls in parallel for each package → results scored against thresholds (1k+ weekly downloads, 30+ days old, < 2 years stale, 1+ maintainers, ≤ 30 deps, no install scripts, not deprecated, license set, no advisories, no typosquat) → if any check fails, JSON written to stdout with `permissionDecision: 'ask'` and a human-readable report → Claude Code shows the report and prompts the user. **Fails open** — any timeout or error silently exits 0.

### External API Calls

- `GET https://registry.npmjs.org/{package}` — full package metadata (triggered: every `npm install` on a `Bash` tool call)
- `GET https://api.npmjs.org/downloads/point/last-week/{package}` — weekly download count (same trigger)
- `GET https://registry.npmjs.org/-/npm/v1/security/advisories?package={package}&perPage=5` — known advisories (same trigger)

### Accepted Risks

- **Fails open by design** — every API call has a 10s timeout and any failure (network, rate-limit, parse error) silently `process.exit(0)`. Trade-off: a malicious package install proceeds if npm registry is unreachable, but the hook can never block the user from working offline. Documented in README.
- **Hardcoded popular-package list** — `POPULAR_PACKAGES` (~70 entries) used for Levenshtein typosquat detection is static and grows stale. Acceptable: the list covers the highest-value squat targets, and the hook is layered with download/age/maintainer/advisory checks.
- **Public repo with no secrets** — repo contains only the hook, installer, and docs. No tokens, no env vars, no credentials anywhere in source or git history (verified: AKIA, sk-, ghp\_, xoxb-, BEGIN PRIVATE KEY all clean).

## Guardrails

### Universal (apply to all projects)

1. Never hardcode API keys or secrets — use `.env` + `.env.example` from first commit
2. Every API route needs CORS origin validation, input validation, and auth
3. Write RLS/Firestore rules the same day you create a table
4. Never use `innerHTML` with dynamic data — use `textContent` or framework escaping
5. API proxies must restrict destination URLs with an allowlist (SSRF prevention)
6. Auth cookies must contain signed claims (HMAC), not plain booleans
7. If a secret was ever committed to a public repo, rotate it immediately
8. No `console.log` with sensitive data in production
9. Run `npx prettier --write .` before committing — keep a `.prettierrc` in the repo root

### Project-Specific

- **Public repo** — never add credentials, tokens, or secrets to any file. The repo's value is its auditability; treat it as adversary-readable.
- **Fails open is load-bearing** — do not change the silent-on-error behavior in `npm-install-checker.js` without updating the README and testing offline / rate-limited scenarios. The whole tool's UX contract is "never blocks the user, only warns."
- **POPULAR_PACKAGES list** — when adding entries, keep `length >= 4` filter intact (the `.filter()` call at the bottom). Short names produce too many false-positive Levenshtein matches.
- **`install.js` writes to `~/.claude/settings.json`** — this is the user's global Claude Code config. Any change must be idempotent (re-runnable) and must not duplicate hook entries on update; current code uses an `alreadyRegistered` check.
- **Add a `.gitignore` before adding any build artifacts or .env files** — currently the only thing keeping `node_modules/` out of commits is manual git status discipline.
